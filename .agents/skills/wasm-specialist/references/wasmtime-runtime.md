# Wasmtime Runtime

The wasmtime runtime is the core of any WASM host application. This chapter covers Engine/Store/Linker setup, the `bindgen!` macro, pre-instantiation, fuel metering, and async execution patterns.

## 1.1 Engine Configuration

The `Engine` is the global compilation context. It holds configuration that applies to all compiled modules and components.

```rust
use wasmtime::{Config, Engine};

let mut config = Config::new();

// Enable Component Model support (required for WIT-based components)
config.wasm_component_model(true);

// Enable async support (required if using tokio or async host functions)
config.async_support(true);

// Optional: enable parallel compilation for faster startup
config.parallel_compilation(true);

// Optional: enable module caching to avoid recompilation
config.cache_config_load_default()?;

let engine = Engine::new(&config)?;
```

### Key Config Options

| Option | Purpose | Default |
|---|---|---|
| `wasm_component_model(true)` | Enable Component Model support | `false` |
| `async_support(true)` | Enable async instantiation and execution | `false` |
| `parallel_compilation(true)` | Use multiple threads for compilation | `true` |
| `cache_config_load_default()` | Cache compiled modules to disk | disabled |
| `epoch_interruption(true)` | Enable epoch-based interruption | `false` |
| `consume_fuel(true)` | Enable fuel-based execution metering | `false` |

### Engine Reuse

An `Engine` is expensive to create but cheap to clone (it's internally `Arc`-based). Create one per configuration and reuse it across all stores:

```rust
// GOOD: One engine, many stores
let engine = Engine::new(&config)?;
let store1 = Store::new(&engine, state1);
let store2 = Store::new(&engine, state2);

// BAD: Engine per store
let engine1 = Engine::new(&config)?;
let store1 = Store::new(&engine1, state1);
let engine2 = Engine::new(&config)?; // Wasteful
let store2 = Store::new(&engine2, state2);
```

## 1.2 Store Lifecycle and State

The `Store` holds per-instance state. It owns the runtime data for WASM instances -- linear memories, tables, globals, and your custom host state.

```rust
use wasmtime::Store;
use wasmtime_wasi::{WasiCtx, WasiCtxBuilder, WasiView, WasiCtxView, ResourceTable};

// Define your host state struct
struct MyState {
    ctx: WasiCtx,
    table: ResourceTable,
    // Your custom state here
    request_count: u64,
}

// Implement WasiView so wasmtime-wasi can access WASI state
impl WasiView for MyState {
    fn ctx(&mut self) -> WasiCtxView<'_> {
        self.ctx.as_view(&mut self.table)
    }
}

// Build WASI context with specific capabilities
let wasi_ctx = WasiCtxBuilder::new()
    .inherit_stdio()
    .build();

let state = MyState {
    ctx: wasi_ctx,
    table: ResourceTable::new(),
    request_count: 0,
};

let mut store = Store::new(&engine, state);
```

### Accessing Host State

From within host function implementations, access state via the store:

```rust
// In a host function implementation
fn my_host_func(caller: &mut impl AsContextMut<Data = MyState>) {
    let state = caller.as_context_mut().data_mut();
    state.request_count += 1;
}
```

### Store Limits

Set resource limits to prevent runaway guests:

```rust
use wasmtime::StoreLimitsBuilder;

let limits = StoreLimitsBuilder::new()
    .memory_size(16 * 1024 * 1024) // 16 MB max memory
    .table_elements(10_000)         // Max table entries
    .instances(10)                  // Max concurrent instances
    .build();

store.limiter(|_| &limits);
```

## 1.3 Linker Setup

The `Linker` connects host-provided imports to guest expectations. For Component Model components, use `component::Linker`:

```rust
use wasmtime::component::Linker;

let mut linker: Linker<MyState> = Linker::new(&engine);

// Add WASI imports
wasmtime_wasi::p2::add_to_linker_async(&mut linker)?;

// Add custom host interfaces (generated by bindgen!)
MyCustomInterface::add_to_linker(&mut linker, |state: &mut MyState| state)?;
```

### Async vs Sync

Choose based on your runtime:

```rust
// For async runtimes (tokio)
wasmtime_wasi::p2::add_to_linker_async(&mut linker)?;

// For sync/blocking contexts
wasmtime_wasi::p2::add_to_linker_sync(&mut linker)?;
```

Do not mix async and sync linking in the same linker -- pick one consistently.

## 1.4 The `bindgen!` Macro

`wasmtime::component::bindgen!` generates type-safe Rust bindings from WIT definitions for the **host side**. This is different from `wit_bindgen::generate!` which is for the **guest side**.

### Basic Usage

```rust
wasmtime::component::bindgen!({
    path: "wit",
    world: "my-world",
});
```

### Inline WIT (useful for tests)

```rust
wasmtime::component::bindgen!({
    inline: "
        package test:inline;
        world test-world {
            export greet: interface {
                greet: func(name: string) -> string;
            }
        }
    ",
});
```

### The `with` Key for Type Remapping

Reuse bindings from other crates instead of regenerating them:

```rust
wasmtime::component::bindgen!({
    path: "wit",
    world: "wasi:http/proxy",
    with: {
        // Reuse wasmtime-wasi bindings
        "wasi:io": wasmtime_wasi::p2::bindings::io,
        "wasi:cli": wasmtime_wasi::p2::bindings::cli,

        // Map WIT resources to concrete Rust types
        "wasi:http/types/outgoing-body": body::HostOutgoingBody,
        "wasi:http/types/incoming-request": types::HostIncomingRequest,
    },
});
```

### Trappable Errors

Convert WIT errors into richer Rust error types:

```rust
wasmtime::component::bindgen!({
    path: "wit",
    world: "wasi:keyvalue/imports",
    trappable_error_type: {
        "wasi:keyvalue/store/error" => crate::Error,
    },
});
```

This allows host implementations to return `crate::Error` which can convert to either a WIT-level error or a WebAssembly trap.

### Import Flags

| Flag | Meaning |
|---|---|
| `async` | Host function is `async` |
| `store` | Host function gets access to the `Store` |
| `trappable` | Return type wrapped in `wasmtime::Result<T>` |
| `tracing` | Emit tracing spans for calls |
| `verbose_tracing` | Include list values in traces |

```rust
wasmtime::component::bindgen!({
    path: "wit",
    world: "my-world",
    imports: {
        default: trappable | tracing,
        "wasi:io/poll/poll": async | trappable,
    },
    exports: { default: async },
});
```

### Debug Bindings

Set `WASMTIME_DEBUG_BINDGEN=1` environment variable to write generated code to disk. This helps when debugging confusing trait bounds or type mismatches.

## 1.5 Component Loading and Instantiation

### Basic Pattern

```rust
use wasmtime::component::Component;

// Load from file
let component = Component::from_file(&engine, "path/to/component.wasm")?;

// Or load from bytes
let wasm_bytes = std::fs::read("component.wasm")?;
let component = Component::new(&engine, &wasm_bytes)?;

// Instantiate
let instance = linker.instantiate_async(&mut store, &component).await?;
```

### Pre-Instantiation for Performance

Use `instantiate_pre` to front-load validation and linking. The `Pre` object can be reused across many instantiations:

```rust
// Do expensive work once
let pre = linker.instantiate_pre(&component)?;

// Reuse for each new instance (much faster)
let instance1 = pre.instantiate_async(&mut store1).await?;
let instance2 = pre.instantiate_async(&mut store2).await?;
```

For typed worlds (generated by `bindgen!`), use the generated `*Pre` types:

```rust
let command_pre = CommandPre::new(linker.instantiate_pre(&component)?)?;
let command = command_pre.instantiate_async(&mut store).await?;
```

## 1.6 Fuel-Based Execution Metering

Fuel limits how many WASM instructions can execute, preventing infinite loops:

```rust
let mut config = Config::new();
config.consume_fuel(true);
let engine = Engine::new(&config)?;

let mut store = Store::new(&engine, state);
store.set_fuel(10_000)?; // Allow 10,000 units of fuel

// When fuel runs out, execution traps with an error
match instance.call_async(&mut store, "process", &[], &mut []).await {
    Err(e) if e.to_string().contains("fuel") => {
        println!("Guest exceeded fuel limit");
    }
    other => { /* handle normally */ }
}
```

### Fuel vs Epochs

| Feature | Fuel | Epochs |
|---|---|---|
| Granularity | Per-instruction | Time-based |
| Overhead | Higher (checked per instruction) | Lower (checked at back-edges) |
| Determinism | Deterministic | Non-deterministic |
| Use case | Precise metering, billing | Timeouts, cooperative scheduling |

```rust
// Epoch-based interruption
config.epoch_interruption(true);

store.epoch_deadline_async_yield_and_update(10); // Yield after 10 epoch ticks

// In another thread/task, advance the epoch
engine.increment_epoch();
```

## 1.7 Resource Table Pattern

When implementing WIT resources on the host side, use `ResourceTable` to manage resource handles:

```rust
use wasmtime::component::{Resource, ResourceTable};

struct MyHost {
    table: ResourceTable,
}

// WIT: resource engine { constructor(); push-operand: func(operand: u32); }
impl HostEngine for MyHost {
    fn new(&mut self) -> wasmtime::Result<Resource<CalcEngine>> {
        Ok(self.table.push(CalcEngine::new())?)
    }

    fn push_operand(&mut self, self_: Resource<CalcEngine>, operand: u32) -> wasmtime::Result<()> {
        let engine = self.table.get_mut(&self_)?;
        engine.stack.push(operand);
        Ok(())
    }

    fn drop(&mut self, rep: Resource<CalcEngine>) -> wasmtime::Result<()> {
        self.table.delete(rep)?;
        Ok(())
    }
}
```

### Resource Lifecycle

1. Host creates resource, pushes to `ResourceTable`, gets `Resource<T>` handle
2. Handle is passed to guest as an opaque `u32` index
3. Guest calls methods, passing handle back to host
4. Host looks up concrete type via `table.get(&handle)` or `table.get_mut(&handle)`
5. When guest drops the resource, host's `drop` method is called
